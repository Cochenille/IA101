Séance 1 — Comprendre la machine et bien formuler sa demande ​

Lundi 30 novembre · 3 heures

Objectifs ​

À la fin de la séance, vous pouvez :

  • expliquer ce qu'est un token, une fenêtre de contexte, et pourquoi un modèle peut répondre avec assurance quelque chose de faux ;
  • distinguer un chat d'un agent (un modèle, des outils et une boucle) ;
  • rédiger une demande qui donne l'objectif, le contexte, les contraintes et les critères de réussite ;
  • utiliser Git comme filet de sécurité quand un agent modifie votre code.

Avant la séance ​

  • Votre demande GitHub Education est approuvée et Copilot est activé sur votre compte.
  • Visual Studio 2026 et le SDK .NET 10 sont installés (dotnet --list-sdks).
  • Vous avez lu la mise en situation dans le README de Jumelo.

2. Ce qu'il y a dans la boîte ​

Le jeu du mot suivant ​

Complétez à voix haute : « Il était une… »

Votre cellulaire fait la même chose depuis des années. Un grand modèle de langage (LLM) aussi, mais en beaucoup plus gros : il a lu une immense quantité de texte et de code, et il a appris quelle suite est probable après n'importe quel début.

Il ne cherche pas la bonne réponse, il prédit la suite la plus vraisemblable, puis recommence avec un mot de plus.

Quel est le mot suivant ?

Il était une  ? 

fois95 %
autre2 %
histoire2 %
princesse1 %
erreur1 %

Probabilités inventées pour l'illustration. À température 0, le modèle prend toujours le plus probable ; plus la température monte, plus les choix improbables sortent.

Mini-exercice (3 min)

  1. Choisissez « La capitale de l'Australie est », réglez la température à 0 et générez 20 fois. Puis à 1,5. Qu'est-ce qui change ?
  2. À température normale, le modèle répond « Sydney » environ une fois sur cinq. A-t-il l'air moins sûr de lui quand il se trompe ?
  3. Pourquoi la même question posée deux fois à Copilot donne-t-elle deux réponses différentes ?

Les tokens ​

Le modèle ne lit pas des lettres ni des mots, mais des tokens : des morceaux de texte d'environ 3 à 4 caractères en anglais. Tout se compte en tokens : ce que le modèle peut lire, ce qu'il peut écrire, et ce que ça coûte.

Découpeur de tokens

83 caractères
… caractères par token

Chaque couleur est un token. Le symbole ␣ est une espace. Le modèle ne voit jamais vos lettres : il voit la suite de numéros.

  • Pourquoi le français coûte-t-il plus de tokens que l'anglais ?
  • Comment le nombre 12345678 est-il découpé ? Qu'est-ce que ça laisse deviner sur la capacité d'un modèle à calculer ?
  • Changez de découpeur (GPT-4 au lieu de GPT-4o) sur la phrase en français et sur les émojis. Que remarquez-vous ?

À retenir

Chaque modèle a son propre découpeur. Le nombre exact change, mais l'ordre de grandeur reste : environ 4 caractères par token pour du texte courant.

La fenêtre de contexte ​

Le modèle n'a aucune mémoire entre deux requêtes. À chaque fois, l'outil lui renvoie tout ce qu'il doit savoir : ses consignes, la conversation, les fichiers ouverts, votre question. Cet ensemble s'appelle le contexte, et sa taille maximale, la fenêtre de contexte.

Chaque requête renvoie tout le contexte : une longue conversation coûte de plus en plus cher.

Nombres approximatifs. La solution Jumelo complète fait environ 20 500 tokens. La taille réelle de la fenêtre varie selon le modèle, de quelques dizaines de milliers à plus d'un million de tokens.

Mini-exercice (3 min)

  1. Avec la fenêtre de 32 000 tokens, posez votre question, ajoutez JumelageViewModel.cs, collez la documentation d'EF Core, puis ajoutez toute la solution Jumelo. Que devient votre question ? Essayez ensuite le journal d'exécution.
  2. Passez à 128 000. Combien d'éléments pouvez-vous ajouter avant le premier débordement ?
  3. Regardez le compteur « Tokens envoyés au total ». Pourquoi une longue conversation coûte-t-elle de plus en plus cher ?

Plus de contexte n'est pas toujours mieux

Même sans déborder, un modèle noyé sous des milliers de lignes inutiles repère moins bien ce qui compte. Donnez-lui le bon contexte, pas tout le contexte.

Quand le modèle invente ​

Un modèle produit la suite la plus plausible, pas la plus vraie. Quand il ne sait pas, il ne se tait pas : il invente quelque chose qui a l'air juste, avec la même assurance que le reste. On appelle ça une hallucination.

Existe ou inventé ?0 / 0

Un assistant vous a proposé chacune de ces lignes, avec la même assurance. Lesquelles compilent ?

etudiants.RemoveAll(e => e.Moyenne < 60);
var titre = offre.Titre.Truncate(30);
var meilleur = etudiants.MaxBy(e => e.Moyenne);
[ObservableProperty]
private string nom;
etudiants.RemoveWhere(e => e.Moyenne < 60);
CommandManager.InvalidateRequerySuggested();
MessageBox.Show("Jumelage créé");
// dans JumelageViewModel
var moyenne = Math.Clamp(valeur, 0, 100);

Les hallucinations les plus dangereuses ne sont pas les plus folles : ce sont celles qui ressemblent à du vrai code. Une méthode qui existe sur un type voisin, un paquet NuGet au nom crédible, une option de configuration qui « devrait » exister. Le compilateur attrape les premières ; pour un paquet inventé, des pirates publient parfois un vrai paquet malveillant sous ce nom.

Chat ou agent ? ​

Un chat répond à votre message, puis attend. Un agent, c'est un modèle à qui on donne des outils (lire un fichier, chercher, modifier, exécuter une commande) et qu'on laisse travailler en boucle jusqu'à ce que l'objectif soit atteint.

La boucle d'un agent, pas à pas
  1. Vous« Dans l'écran Jumelage, affiche « Complet » au lieu de « 0 place(s) restante(s) ». Les tests doivent passer. »
1 / 13

Dans un chat, c'est vous qui faites la boucle : copier, coller, compiler, recoller l'erreur. Un agent la fait seul, avec ses outils. Il vous reste la dernière étape.

Mini-exercice (2 min) : pendant le diagnostic, combien de fois avez-vous fait la boucle à la main (copier, coller, compiler, recoller l'erreur) ?

Dans Copilot, ce choix se fait dans la fenêtre de chat :

ModeCe qu'il faitQuand l'utiliser
AskRépond à vos questions, sans toucher à vos fichiers.Comprendre du code, explorer une idée.
AgentLit, cherche, modifie des fichiers et exécute des commandes, en boucle.Réaliser une tâche complète et vérifiable.

Choisir son modèle ​

Copilot vous laisse choisir parmi plusieurs modèles. Certains comptent comme des requêtes premium : chaque utilisation est retirée d'un quota mensuel, parfois multipliée selon le modèle. Consultez les paramètres Copilot de votre compte GitHub pour connaître votre quota.

  • Une question simple ou une petite modification : un modèle rapide suffit.
  • Une tâche longue en mode Agent, du débogage difficile : un modèle plus puissant vaut la requête premium.
  • Si un modèle tourne en rond, changer de modèle ou repartir d'une conversation neuve aide souvent.

3. Anatomie d'une bonne demande ​

Une bonne demande répond à quatre questions. Activez-les une à une pour voir la requête se construire :

Anatomie d'une demande

Il y a un bug dans l'affichage des places. Corrige.

L'agent va deviner ce que vous voulez dire par « bug », où il se trouve et quand s'arrêter.

Exercice : vos propres requêtes (15 min)

  1. Ouvrez votre diagnostic.md. Pour chaque requête, cochez dans la marge les éléments présents : Objectif, Contexte, Contraintes, Réussite.
  2. Choisissez votre requête la plus faible et réécrivez-la avec les quatre éléments, sous une section ## Requête réécrite.
  3. Échangez avec votre voisin : lisez sa requête réécrite. Sauriez-vous faire la tâche sans lui poser de question ? Sinon, il manque encore quelque chose.

4. Activité : Copilot en mode Agent sur Jumelo ​

Ouvrez votre dépôt Jumelo dans Visual Studio 2026, puis la fenêtre GitHub Copilot Chat, en mode Agent.

Étape 1 : comprendre avant de modifier (10 min) ​

Demandez à l'agent d'expliquer l'architecture sans modifier aucun fichier. Par exemple :

Explique-moi l'architecture de Jumelo : les couches, comment l'écran Jumelage obtient ses données, et où sont les règles qui décident si un étudiant peut être jumelé à une offre. Ne modifie aucun fichier. Cite les fichiers.

Point de contrôle : sur une feuille, dessinez le chemin d'une donnée, de la base SQLite jusqu'à l'écran Jumelage. Ouvrez deux des fichiers cités pour vérifier que l'agent n'a rien inventé.

Étape 2 : un test rouge (20 min) ​

Dans un terminal, à la racine du dépôt :

powershell
dotnet test

Un test échoue. Avec l'agent, trouvez pourquoi, et corrigez le code, pas le test. Rédigez votre demande avec les quatre éléments : n'oubliez pas les contraintes.

Ne jamais affaiblir un test

Un agent à qui l'on demande « fais passer le test » peut modifier le test au lieu du code. Vous restez responsable du code que vous acceptez.

Étape 3 : relire, puis commit (10 min) ​

powershell
git diff
  • Quels fichiers ont changé ? Est-ce que chacun avait une raison de changer ?
  • Le fichier de test est-il intact ?
  • Relancez dotnet test vous-même.

Faites un commit avec un message qui explique ce qui a changé et pourquoi.

Git, votre filet de sécurité

Faites un commit avant de lancer l'agent sur une tâche. S'il part dans la mauvaise direction, git restore . efface tout et vous recommencez avec une meilleure demande.

Étape 4 : retour au diagnostic (10 min) ​

Reprenez le problème de Geneviève. Ce coup-ci : un commit avant de commencer, une demande avec les quatre éléments, le diff relu et l'application lancée pour vérifier à l'écran. Notez dans diagnostic.md ce qui a changé dans votre façon de faire.

5. Billet de sortie ​

Billet de sortie

1Vous posez deux fois exactement la même question à Copilot et obtenez deux réponses différentes. Pourquoi ?

2Copilot vous propose, avec assurance, etudiants.RemoveWhere(...) sur une List<Etudiant>. Que s'est-il passé ?

3Après deux heures dans la même conversation, l'agent ne respecte plus une consigne donnée au début. L'explication la plus probable ?

4Qu'est-ce qui distingue un agent d'un chat ?

5L'agent annonce : « Tous les tests passent, le problème est corrigé. » Que faites-vous ?

Notions à retenir ​

  • Un modèle prédit la suite d'un texte, token par token ; ses réponses ne sont pas déterministes.
  • Tout ce que le modèle « sait » de votre projet est dans sa fenêtre de contexte. Ce qui n'y est pas, il le devine.
  • Un modèle produit du plausible, pas du vrai : le compilateur, les tests et vos yeux vérifient.
  • Un agent, c'est un modèle, des outils et une boucle. Il vous reste toujours la dernière étape : vérifier.
  • Une bonne demande dit quoi, pourquoi, avec quelles contraintes et comment savoir que c'est réussi.
  • Petits commits fréquents : on peut toujours revenir en arrière.
